# ETL DATA PIPELINE POC Processing The New York City Taxi and Limousine Commission (TLC) Trip Record Data

Technology stack: python, polars, pytest, airflow, docker

Data source: https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page

To run this project please install [docker](https://www.docker.com/get-started/)

As this is only POC, no QA has been performed. This POC works mainly as a showcase of working etl pipeline. Results of the
etl operations are not guaranteed to be correct!

# General architecture
Orchestration and ETL processes are defined in different packages separating orchestration from ETL code (python scripts).
Both are separately dockerized. Docker definitions along we exact commands to be found in following *Running* section.

# Running
1. **build python project** (from root): docker build -t nyc-taxi-etl:latest .
1. **build airflow project** (from root/airflow): docker compose build airflow
1. **run Airflow UI** (from root/airflow): docker compose up
1. **to open AF UI access local host via web browser**: http://0.0.0.0:8080/
   - **Airlflow UI credentials (generated dynamically) to be found in Airflow logs, example**: 
        `airflow-1  | Simple auth manager | Password for user 'admin': TmhM8przdKzsqwpA`

Or run python scripts independently after step 1, e.g.:
docker run --rm -v "$(pwd)/data:/app/data" nyc-taxi-etl:latest python src/etl/dq/report_taxi_green.py --date=20260826 --year=2026 --month=1
docker run --rm -v "$(pwd)/data:/app/data" nyc-taxi-etl:latest python src/etl/processing/process_taxi.py --date=20260826 --year=2026 --month=1
docker run --rm -v "$(pwd)/data:/app/data" nyc-taxi-etl:latest python src/etl/reports/report.py --date=20260826 --year=2026 --month=1
docker run --rm -v "$(pwd)/data:/app/data" nyc-taxi-etl:latest python src/etl/reports/report_read.py --date=20260826

# Project structure
Task was to provide single repository containing both ETL code and orchestration. Good practice is to separate those 
into different repositories.

## airflow
- containing:
  - docker files for building and running the environment
  - DAG folder with DAG *nyc_taxi_etl.py* defining ETL pipeline with following tasks:
    - printing context attributes (input arguments) as a started point
    - DQ tasks for each data source
    - data source processing tasks
    - report aggregation task
    - and finally print report generated by previous task for quick result overview

## data
- location for all input and output files
- mounted to docker container as external volume, this way the output is persisted even after docker container is terminated
- content folder structure must be created in advance

## src
ETL python code and unit tests

### etl 
- etl operations definitions logically divided into following packages:
  - dq - source data quality check reports
    - currently just printing the results into log
    - depending on a situation assert operations can be used to stop further processing in case serious issues found - not implemented
    - depending on requirement any kind of notification can be triggered (mail/slack/teams/etc.) - not implemented
  - processing - scripts for transforming source data into clean valid data suitable for reporting
  - reports - report aggregations based on transformed data 
## tests
  - unit - code testing for manual or CICD purposes

More specifics in following sections.


# Data structure
- data structure (input/output folders and partitions) is static and has to be created in advance as polars fails on 
storing data to non-existent directory. That means with processing new month source data, new partitions (monthly/daily)
have to be created in order to read and store the data. Valid data structure is as follows:

- data/
  - input/
    - month=*yyymm*/
      - *\*.parquet*
    - taxi_zone_lookup.csv
  - output/
    - report/
      - day=*yyyymmdd*
        - *result.parquet*
    - transformed/
      - trips/
        - rental/
          - day=*yyyymmdd*
            - transformed.parquet
        - taxi/
          - day=*yyyymmdd*
            - transformed.parquet
- example: data_structure.zip

Source data are partitioned by year and month (e.g. 202601). Project is using daily partitioning for data output.
It is topic for discussion whether it should rather stick to monthly instead considering many aspects and expactations
of final implementation.

# Scheduling
Defined by Airflow DAG attribute `schedule="0 1 1 * *"` (Every first day of month at 01:00 AM) expecting Airflow 
environment is up and running. Also, possible to trigger manually in Airflow UI. DAG expects 3 values:
- processing date (used mainly to store processed/aggregated data into daily partition)
- month of the source data (used to define source data partition)
- year of the source data (used to define source data partition)


# Deployment - DRAFT!
Considered target system - AWS.
Deployment steps defined as a draft scripts in `./deploy`:
  - airflow code copy/sync to AWS S3: *deploy/deploy_airflow_s3.sh*
  - config files deployment to AWS S3: *deploy/deploy_configs_s3.sh*
  - etl code copy/sync to AWS S3: *deploy/deploy_etl_s3.sh*
  - docker push operation to container registries: 
    - Git (GCR) - building image: *deploy/docker_push_gcr.sh*
    - AWS ECR - reading image from GCR: *deploy/docker_push_ecr.sh*

ETL code can be deployed either by copying project structure into S3 bucket or built into docker image and pushed to 
remote docker registry.
Scripts are prepared to be used also in CICD within deployment stage.

# Data limit
To be able to run this project locally with limited resources, records limit is applied when reading the input data.
Records limit value (50000) is defined in `scr/etl/__init__.py` as `DATA_RECORDS_LIMIT` constant.

For higher data volumes it is expected this solution to be deployed into environment with sufficient resources.
